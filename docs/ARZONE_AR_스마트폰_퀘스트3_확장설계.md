# ARZONE AR 개발 설계서 — 스마트폰 → Meta Quest 3 확장 전략

> 작성일: 2026-07-17
> 범위: AR 클라이언트 개발 파트 (인식 · 배치 · 3D UI · 크로스플랫폼)
> 목표: **스마트폰 우선 출시 → 약 1개월 후 Meta Quest 3 확장**, 이때 **재작업 최소화**

## 1. 한눈에 보는 결정 요약

| 항목 | 결정 | 비용 | Quest 확장 |
|---|---|---|---|
| 엔진 | Unity 6 LTS + AR Foundation + OpenXR | 무료 | 단일 코드베이스 |
| 피규어 인식 | **정면 2D 이미지 인식(Image Target), 최초 1회 해금** | **무료** (Vuforia Basic 또는 AR Foundation) | **불필요** — 폰서 해금, Quest는 호출만 |
| 콘텐츠 배치 | 평면(바닥) 인식 + 제스처 배치 | 무료 | **동일 API 그대로** |
| 룸 구조 | AR 허브 → Stage / Album / Gallery / Avatar | — | 100% 공유 |
| 인증 | QR/NFC 등 (AR과 분리, 최초 1회) | — | 별도 트랙 |

핵심 원칙 한 줄:

> **스택을 통일하지 말고, "입력·패스스루" 인터페이스를 격리한다.**
> 피규어 인식은 폰 최초 1회 해금(계정 귀속)이라 **Quest는 인식 자체가 없다.** 그러면 Quest 확장 = 입력·패스스루 구현 + 월드공간 UI 재호스트 + 튜닝. 그 위 로직·콘텐츠는 그대로.

## 2. 왜 이 구성인가 (배경)

- **피규어 정면 2D 인식**: 3D 형상 인식(Model Target)은 유료(Premium). 인식이 **최초 1회 해금용**이라 정면 유도만으로 충분 → 무료 Image Target으로 대체(뒤·옆 인식은 요구사항 아님). 인식 SDK는 **Vuforia Basic 또는 AR Foundation** 모두 2D는 무료 — 배치·평면과 **단일 프레임워크로 통일** 권장(혼용 시 AR 세션 2개 통합 부담).
- **인식은 폰 최초 1회, 계정 귀속**: 한 번 해금하면 이후는 UI에서 호출(소환). 따라서 **Quest에서는 피규어 인식이 전혀 필요 없다** — 로그인 → 해금된 콘텐츠 호출.
- **평면 기반 배치**: 실제 와이어프레임의 AR UX가 "바닥 인식 → 콘텐츠 배치"다. 이 방식은 AR Foundation이 폰·Quest를 **동일 API로 공식 지원**하므로 확장에 가장 유리.
- **연속 추적 배제**: 큐브/피규어를 계속 추적하며 돌리는 방식은 가림·모션블러로 불안정하고 Quest에서 자체 구현 부담이 큼. 1회 인식 + 평면 배치로 이 리스크를 원천 제거.

```

│ 공유 레이어 (폰 · Quest 90%+ 재사용)             │

│  · AR 캡쳐, 친밀도/미션 연동                      │
│  · 백엔드 클라이언트 (소유권/인증/DRM/콘텐츠)     │
├───────────────────────────────────────────────┤
│ 인터페이스 경계 (여기만 플랫폼별로 갈림)          │
│  IFigureDetector   · IPointerInput              │
│  IPassthrough      · (IPlaneSource는 AF가 흡수)  │
├──────────────────────┬────────────────────────┤
│ 폰 구현              │ Quest 3 구현             │
│  ARKit / ARCore      │  Meta OpenXR             │
│  Image Target 정면   │  QR/PCA 또는 수동 소환    │
│  Touch 입력          │  Hand/Controller 입력    │
└──────────────────────┴────────────────────────┘
```

### 공유되는 것 (플랫폼 무관)
- 소환·허브 상태머신, 룸 이동 로직
- 3D 콘텐츠, 룸 Prefab, UI 프리팹
- **평면 배치 파이프라인** — `ARPlaneManager` / `ARRaycastManager` / `ARAnchorManager` 는 AR Foundation이 ARKit·ARCore·Meta OpenXR에서 **동일 API**로 제공 → 코드 공유
- 백엔드 연동, 캡쳐, 미션/친밀도

### 인터페이스로 격리되는 것 (플랫폼별 구현)
| 인터페이스 | 역할 | 폰 구현 | Quest 구현 |
|---|---|---|---|
| `IFigureDetector` | 피규어 최초 1회 해금 → 초기 포즈 | Image Target (Vuforia Basic 또는 AF, 무료) | **불필요** — 해금 콘텐츠 호출 |
| `IPointerInput` | 회전·포인팅·선택 | Touch | Hand ray / Controller |
| `IPassthrough` | 배경 영상 | 카메라 배경(자동) | Meta Passthrough |

## 4. 크로스플랫폼 대응표 (기능 단위)

| 기능 | 폰 (ARKit/ARCore) | Quest 3 (Meta OpenXR) | 재사용 |
|---|---|---|---|
| 평면 인식 | 런타임 실시간 스캔 | Room Setup(Scene Model)에서 조회 | ✅ 코드 동일, UX만 상이 |
| 레이캐스트 배치 | ✅ | ✅ | ✅ |
| 앵커 고정 | ✅ | ✅ | ✅ |
| 패스스루 배경 | 카메라 자동 | Meta Passthrough | 인터페이스 |
| **피규어 정면 인식** | ✅ Image Target(무료) | ⚠️ PCA + OpenCV 정면 이미지 매칭(커스텀) | ⚠️ 구현체 교체 |
| 입력 | 터치 | 핸드/컨트롤러 | ⚠️ 구현체 교체 |
| 3D 콘텐츠/룸/로직 | — | — | ✅ 100% |

> ⚠️ **핵심 주의**: 현재 Meta OpenXR의 AR Foundation provider는 **2D 이미지 트래킹(`ARTrackedImageManager`)을 지원하지 않는다.** 따라서 폰의 인식 코드는 그대로 넘어가지 않고, Quest에서는 **Passthrough Camera API로 프레임을 받아 OpenCV 특징점 매칭(ORB/AKAZE)으로 정면 이미지를 직접 검출**한다. 인식이 **1회 · 러프 포즈 허용**이라 연속 추적보다 부담이 작지만, QR 대비 Quest 개발량은 늘어난다(대신 QR 없는 일관된 UX 확보).

## 5. 피규어 정면 인식 구현

동일한 참조 이미지(피규어 정면)를 양 플랫폼이 공유하고, 검출 엔진만 다르다. 두 구현 모두 `IFigureDetector.DetectFrontOnce() → (Pose, confidence)` 계약을 만족한다.

### 5.1 폰 (ARKit / ARCore — 무료)
1. **참조 이미지 등록**: 피규어 정면을 촬영/렌더 → `XRReferenceImageLibrary`에 등록 (실물 크기 지정)
2. **정면 게이트**: `ARTrackedImageManager`가 이미지를 검출하면, 추적된 이미지의 법선과 카메라 방향의 각도를 계산 → **정면(±허용각) 일 때만** 유효 처리
3. **1회 확정**: 유효 검출 시 초기 포즈를 앵커로 고정하고 추적 종료 → 이후 피규어를 치워도 무방

### 5.2 Quest 3 (Passthrough Camera API + OpenCV — 커스텀)
1. **참조 특징 사전 추출**: 동일한 정면 이미지에서 ORB/AKAZE 특징점·디스크립터를 미리 추출해 번들
2. **프레임 획득**: PCA로 전방 카메라 프레임 + 카메라 내부 파라미터(intrinsics) 취득
3. **매칭**: 프레임 특징점 ↔ 참조 디스크립터 매칭 → 충분한 인라이어면 호모그래피 추정 → `solvePnP`로 러프 포즈
4. **1회 확정**: 임계값 초과 시 검출 성공으로 확정, 앵커 고정 (연속 추적 불필요 → 성능·정확도 부담 완화)
5. 참고 구현: `QuestCameraKit`, `QuestArUcoMarkerTracking`(마커→자연특징 매칭으로 응용)

> 공통 소환 흐름: 검출 성공 → 인증(소유권) 확인 → 그 앵커 자리에서 콘텐츠 소환 → 허브 진입.

### 5.3 인식률을 위한 디자인 요구사항 (디자인팀 전달 — **필수**)
- 정면 아트를 **무광(matte) · 고대비 · 디테일 풍부**하게. 매끈한 단색 표면은 특징점 부족으로 인식 불안정. **Quest 패스스루 카메라는 폰보다 화질·정밀도가 낮아 이 요구가 더 중요**하다 (특징점이 넉넉해야 OpenCV 매칭이 붙는다).
- 정면 가이드 프레임 UI로 사용자를 정면 정렬 유도
- **실물 프로토타입 확보 즉시** 실기기 인식 테스트 (지금은 렌더 이미지로 예비 검증). 폰·Quest 각각 별도 검증.

## 6. 확장 로드맵 (스마트폰 → Quest 3)

### Phase 0 — 공통 토대 (착수 시)
- Unity 6 LTS 프로젝트 + URP + AR Foundation 설치
- Assembly 분리 (9장) 및 3개 인터페이스 정의 (`IFigureDetector`/`IPointerInput`/`IPassthrough`)
- XR Simulation / Device Simulator 세팅 (Quest 실기기 없이 선개발)

### Phase 1 — 스마트폰 MVP (지금 ~ 출시)
- ARKit/ARCore Image Target으로 **피규어 정면 1회 인식 → 소환**
- **평면 인식 + 제스처 배치** 파이프라인 (레이캐스트·앵커·회전/드래그)
- AR 허브 + 룸 (**Stage 우선**, 이후 Album/Gallery/Avatar)
- 백엔드 연동 (소유권/콘텐츠 접근/캡쳐 저장)
- KPI: 인식 성공률 95%+, 첫 인식 30초 이내

### Phase 2 — Quest 3 확장 (+약 1개월)
1. **Meta OpenXR 패키지 추가**, Quest 빌드 타깃 구성, 패스스루 활성화
2. **평면/레이캐스트/앵커 = 그대로 동작 검증** (Room Setup 기반 평면 대응)
3. `IFigureDetector` → **Quest 구현체 작성** (PCA + OpenCV 정면 이미지 매칭 — Phase 2 최대 신규 작업)
4. `IPointerInput` → **핸드/컨트롤러 구현**
5. UI **거리·스케일·가독성 튜닝** (헤드셋 시야 기준)
6. 룸/콘텐츠/로직/백엔드 → **재사용 (수정 없음)**

## 7. Quest 확장 시 실제 작업 범위 (정직하게)

- 🔴 **새로 작성**: `IFigureDetector` Quest 구현(**PCA + OpenCV 정면 이미지 매칭** — 가장 무거운 신규 작업), `IPointerInput` 핸드 구현, 패스스루 세팅

- ✅ **그대로 재사용**: 소환/허브 상태머신, 룸 4종, 평면 배치 로직, 캡쳐, 미션/친밀도, 백엔드 전부

즉 확장 작업의 대부분은 **인터페이스 구현체 2개 + 튜닝**에 국한된다. 이것이 "인터페이스 격리" 설계의 목적이다.

## 8. 프로젝트 구조 (Unity Assembly Definition)

| 어셈블리 | 책임 | 플랫폼 의존 |
|---|---|---|
| `ARZone.Core` | 소환/허브 상태머신, 룸 이동 로직, 배치 파이프라인(AF 인터페이스 경유) | 없음 |
| `ARZone.Content` | 룸 4종, Prefab, 3D UI | 없음 |
| `ARZone.Platform.Interfaces` | `IFigureDetector`/`IPointerInput`/`IPassthrough` | 없음 |
| `ARZone.Platform.Mobile` | ARKit/ARCore 구현 (Image Target, Touch) | iOS/Android |
| `ARZone.Platform.Quest` | Meta OpenXR 구현 (QR/PCA, Hand, Passthrough) | Quest |
| `ARZone.Backend` | 소유권/인증/DRM/콘텐츠 API 클라이언트 | 없음 |

> 플랫폼 어셈블리는 빌드 타깃별로 include/exclude. `Core`/`Content`는 어떤 플랫폼 코드에도 의존하지 않게 유지 → 재사용 보장.

## 10. 폰 ↔ Quest 대단위 호환성 & Quest 확장 범위 (팀 결정 대기)

**피규어 인식은 호환성 이슈의 작은 일부다.** 더 큰 단위에서 폰↔Quest가 갈리는 지점이 있고, 이것이 확장 규모를 좌우한다.

### 10.1 대단위 호환성 이슈

| # | 이슈 | 폰 | Quest 3 | 심각도 |
|---|---|---|---|---|
| 1 | **UI 시스템** | 2D 스크린 UI | **2D 화면 개념 없음** → 전부 월드공간 패널로 재구성 | 🔴 최대 |
| 2 | **입력 패러다임** | 터치(탭·드래그·핀치) | 핸드/컨트롤러(레이+핀치) | 🔴 큼 |
| 3 | **렌더링/성능** | 모노, 여유 | **스테레오(2×)+72~120Hz 필수**, 모바일 GPU | 🔴 큼 |
| 4 | **결제·계정·NFC** | 앱스토어 IAP, 간편결제, NFC | Meta 스토어, **NFC 없음**, 간편결제 사실상 불가 | 🔴 큼 |
| 5 | **텍스트 입력** | 네이티브 키보드 | 가상 키보드 고통 → 음성 위주 | 🟡 중 |
| 6 | **미디어/DRM** | 표준 플레이어 | 월드공간 스크린, DRM 플러밍 상이 | 🟡 중 |
| 7 | **공간 모델** | 세션마다 실시간 스캔 | Room Setup(사전스캔) + 가구 오클루전 | 🟡 중 |
| 8 | **AR 캡쳐** | 카메라+콘텐츠 스샷 | 헤드셋 뷰 캡쳐, 외부 공유 마찰 | 🟡 중 |
| 9 | **사용 패턴** | 꺼내서 잠깐·매일 | 착용 필요·긴 몰입, "매일 대화"엔 마찰 | 🟡 중 |

### 10.2 핵심 통찰

제일 큰 건 AR이 아니라 **"2D 앱 껍데기"**다. 이 앱은 대부분 평면 화면(홈·마켓·커뮤니티·MY·설정·플레이어)인데 Quest엔 2D 화면 개념 자체가 없어, 전부 월드공간 UI로 옮기는 게 최대 작업이다. 게다가 **결제·NFC·텍스트 입력**은 헤드셋 포팅이 사실상 불가하다. 반면 **백엔드(REST API)는 완전 공유**된다.

### 10.3 Quest 확장 범위 — 3안 (결정 대기)

| 범위안 | Quest에서 하는 것 | 폰에 남기는 것 | 우회하는 문제 | 1달 적합성 |
|---|---|---|---|---|
| **① AR 감상 전용 뷰어** (권장) | 무대·아바타 소환·감상(Stage/Avatar) | 마켓·커뮤니티·결제·계정·설정 | 4·5·6·8·9 통째로 | ✅ 현실적 |
| ② 핵심 기능까지 | AR 감상 + 허브·친밀도·간단 조회 | 결제·긴 텍스트·거래 | 4·5 일부 | 🟡 빠듯 |
| ③ 앱 전체 포팅 | 모든 화면 | 없음 | 없음(정면돌파) | 🔴 비현실적 |

**권장: ① AR 감상 전용 뷰어.** Quest를 "공간에 무대·아바타를 소환해 감상하는 몰입 뷰어"로 한정하면 위 4·5·6·8·9 문제를 통째로 우회하고, 이미 공유되는 AR 코어(평면·배치·룸·백엔드)를 그대로 살릴 수 있다. 거래·커뮤니티·결제는 폰 컴패니언에 유지.

### 10.4 결정 기준

1. Quest에서 사용자가 무엇을 해야 하는가 — 감상만? 거래·커뮤니티도?
2. 1달 일정 현실성 (범위 ③은 UI 전면 재구성 + 결제/텍스트 난제로 비현실적)
3. 심사에서 Quest로 보여줄 데모의 범위

> 이 범위가 정해져야 Phase 2 작업 목록이 확정된다. 미정 시 기본값은 **①(AR 감상 전용)**으로 두고 Phase 1(폰)을 진행한다.
